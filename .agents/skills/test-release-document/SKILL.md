# 提测文档技能

## 目标

只基于仓库当前内容生成测试人员可执行的中文提测单，不臆造未在代码、配置、提交记录或测试中出现的信息。

## 固定输出契约

输出必须是 Markdown，标题必须按以下顺序出现，不能合并、改名、调序或省略：

1. `# {项目名} 提测单`
2. `## 1. 本次开发内容`
3. `## 2. 需求 / Issue`
4. `## 3. 改动范围`
5. `## 4. 接口变化`
6. `## 5. 数据库变化`
7. `## 6. 正常流程`
8. `## 7. 异常流程`
9. `## 8. 测试环境`
10. `## 9. 测试数据`
11. `## 10. 风险点`
12. `## 11. 已知问题`
13. `## 12. 验收标准`

每个章节至少写 1 条；无内容时写“无”或“未提供，待补充”，不得删除章节。

## 固定格式

- `1/2/3/6/7/9/10/11/12`：使用无序列表；流程和验收标准使用可执行的有序列表或复选项。
- `4. 接口变化`：必须使用表格，列固定为“方法 | 路径 | 请求 | 成功响应 | 失败响应”；没有失败响应时写“无/未统一定义”。
- `5. 数据库变化`：必须依次写“数据库”“Migration”“表/字段”“约束/索引”“运行时使用情况”。
- `8. 测试环境`：必须使用表格，行固定为“地址、分支、提交/版本、启动方式、应用运行时、数据库、测试命令”；未知项写“未提供，待补充”。
- 文档末尾不得新增第 13 节或附录；补充信息放入对应章节。

## 范围确认门槛

在读取项目细节或生成提测单前，先确认“本次提测模块范围”。以下情况视为范围未明确：用户只说“根据项目内容/当前代码生成提测单”，但没有点名模块、功能、接口或变更范围。

- 范围未明确时，只提问，不生成文档、不修改文件：`本次提测要覆盖哪些模块或功能？例如：用户 CRUD、健康检查、Flyway 数据库迁移；如果覆盖全部当前变更，请回复“全部”。`
- 用户回复“全部”“全量”“当前所有变更”时，范围确定为仓库当前全部相关变更。
- 用户列出模块、接口、Issue 或文件时，以这些内容作为范围；必要时读取其直接依赖，但不要扩展到无关模块。
- 范围已确定后，在提测单第 3 节“改动范围”首条写明“本次提测范围：……”。
- 不要用 Git 状态、最近提交标题或仓库目录自动替用户决定提测范围；这些只能作为事实依据。

## 工作流

1. 读取项目说明、Git 状态、构建配置、应用配置、控制器、服务、仓储、模型、异常处理、数据库迁移和测试。
2. 追踪每个 API 的请求、成功状态码、响应体、异常来源和全局处理器，禁止凭接口名称猜行为。
3. 区分“已实现”“配置/迁移已提供”“测试已覆盖”“未实现/待补充”；内存实现与数据库迁移并存时必须明确区分。
4. 从真实配置、分支、提交、依赖和测试中填写环境信息；没有证据就写“未提供，待补充”。
5. 生成固定 12 章文档，并逐项检查标题、表格列和必填字段。

## 质量门槛

- API 路径、方法、请求体、响应和错误条件必须与代码一致。
- 异常流程必须覆盖参数错误、资源不存在、请求格式错误和基础设施失败（若适用）。
- 验收标准必须能被测试人员逐项执行，并对应正常/异常流程。
- 不修改代码、配置、迁移或测试；仅写入用户指定的提测文档文件。
