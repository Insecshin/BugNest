# 用户登录设计

## 设计结论

- `Account` 表示登录账户，负责邮箱、密码哈希、唯一用户名、昵称和创建时间。
- `User` 模型和 `MemoryUserRepository` 暂时保留，但与正式注册链路隔离，仅用于兼容或测试。
- 正式链路为 `controller → service → repository`：`AccountController → AccountService → JdbcAccountRepository`。
- 注册接口为 `POST /auth/sign-up`。前端可以多页面收集信息，后端最终只执行一次完整注册。

## 注册请求与响应

请求字段：

```json
{
  "email": "user@example.com",
  "password": "password123",
  "confirmPassword": "password123",
  "nickname": "张三",
  "userName": ""
}
```

- `email`、`password`、`confirmPassword`、`nickname` 必填。
- `userName` 可选；为空时由系统根据 `nickname` 生成。
- `confirmPassword` 只存在于请求 DTO，用于校验，不进入模型和数据库。
- 密码使用 Argon2id 生成哈希，禁止保存或记录明文密码。
- 注册成功返回 `201 Created`，响应 DTO 只返回：

```json
{
  "userId": 123
}
```

- 暂不实现邮箱认证，但邮箱仍需规范化并保持唯一。

## 用户名与昵称

- `nickname` 保存用户原始昵称，必填，允许国际文字，创建后可以修改。
- `user_name` 是唯一登录用户名，只允许小写拉丁字母、数字和下划线，创建后不可修改。
- 注册时 `user_name` 默认由 `nickname` 生成；用户可以在提交前修改默认值。
- 用户手动填写的 `userName` 必须符合 `^[a-z0-9_]+$`，服务端不静默改写。
- `user_name` 的唯一性最终由数据库约束保证；应用层冲突时返回 `409 Conflict`。

## 用户名拉丁化

使用 ICU4J 的 `Any-Latin; Latin-ASCII` 进行跨文字系统转写，不实现自维护的汉字拼音表。

处理顺序：

```text
nickname
→ Unicode NFKC 规范化
→ Any-Latin; Latin-ASCII
→ 转小写
→ 非 a-z、0-9 的字符替换为下划线
→ 合并连续下划线并去除首尾下划线
→ 限制长度
→ 检查唯一性
```

示例：

```text
张三    → zhang_san
Иван    → ivan
Müller  → muller
```

- `user_name` 当前最大长度为 30，生成基础值时为冲突后缀预留长度。
- 若结果为空，使用 `user` 加随机数字作为候选值。
- 若数据库中已存在候选值，追加随机数字并重试；数据库唯一约束是最终保证。
- 已创建的 `user_name` 不因 ICU、Unicode 或转写规则升级而重新生成。
- `nickname` 始终保存原始文字，不能保存拉丁化结果。

## 数据库与迁移

- 当前 `V1__create_app_users.sql` 中的 `username` 仍是现状字段。
- 不修改已执行的 `V1`，通过新的 Flyway 迁移将 `username` 重命名为 `nickname`，并按需要补充非空约束。
- `user_id` 由 PostgreSQL 自动生成；Repository 使用 `INSERT ... RETURNING user_id` 获取新 ID。
- `email` 保存前去除首尾空格并转小写，数据库继续使用大小写不敏感唯一索引。
- 其他业务表使用 `user_id` 建立外键，不引用可变的 `nickname` 或邮箱。

## Repository

- `JdbcAccountRepository` 使用 JDBC 连接 PostgreSQL，并标记为 Spring `@Repository`。
- `MemoryUserRepository` 去除生产环境组件注册，保留为测试或兼容代码。
- 不引入 ORM，也不让旧的 `UserService`、`UserRepository` 参与新的账户注册链路。
- `user_name` 不提供普通用户修改接口；昵称修改单独设计为昵称更新操作。
