# 用户表设计

## 设计结论

用户表命名为 `app_users`。`user_id` 使用数据库生成的 `BIGINT` 作为内部主键；`user_name` 是用户可自定义、大小写敏感与否需统一约定的公开唯一标识，用于 `@nolla0302` 形式的用户引用；`username` 仅作为可重复的显示名称。

当前不额外增加 UUID：业务表统一通过 `user_id` 建立外键，接口对外使用 `user_name`。如果未来需要隐藏用户标识、支持不可变的公开 ID 或跨系统同步，再增加 `public_id UUID`，不替换内部主键。

## 字段

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | `BIGINT` | 主键、数据库自动生成 | 内部关联使用，不对外暴露 |
| `user_name` | `VARCHAR(30)` | 非空、唯一 | 公开用户标识，例如 `nolla0302`；展示时加 `@` |
| `username` | `VARCHAR(50)` | 可空或非空，按注册规则决定 | 用户显示名称，可重复 |
| `email` | `VARCHAR(254)` | 非空、大小写不敏感、唯一 | 登录账号 |
| `password_hash` | `TEXT` | 非空 | Argon2id 哈希，禁止保存明文密码 |
| `created_at` | `TIMESTAMPTZ` | 非空、默认当前时间 | 创建时间 |

## PostgreSQL 建表建议

```sql
CREATE TABLE app_users (
    user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_name VARCHAR(30) NOT NULL,
    username VARCHAR(50),
    email VARCHAR(254) NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT uq_app_users_user_name UNIQUE (user_name),
    CONSTRAINT ck_app_users_user_name_format
        CHECK (user_name ~ '^[a-z0-9_]+$'),
    CONSTRAINT ck_app_users_email_not_blank
        CHECK (length(btrim(email)) > 0),
    CONSTRAINT ck_app_users_username_not_blank
        CHECK (username IS NULL OR length(btrim(username)) > 0)
);

CREATE UNIQUE INDEX uq_app_users_email_ci
    ON app_users (lower(btrim(email)));
```

## 实现约定

- 应用层保存前对 `user_name`、`email`、`username` 执行必要的去除首尾空格；邮箱统一转小写。
- `user_name` 是否大小写不敏感必须固定。推荐只允许小写，避免 `Nolla` 与 `nolla` 被视为不同用户。
- 其他表引用 `app_users.user_id`，不要引用可修改的 `user_name` 或 `email`。
- 重复的 `user_name` 或 `email` 转换为 HTTP `409 Conflict`。
- Argon2id 的参数应由认证配置统一管理；数据库只负责保存哈希字符串。
- `user_name` 是可变的公开句柄，不是永久身份。若未来需要不可变公开 ID，再增加唯一的 `public_id UUID`。
