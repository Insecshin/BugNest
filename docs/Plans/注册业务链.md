# 落地 Account 注册与 PostgreSQL Repository

## 总结

将正式用户链路从内存 `User` 切换为数据库 `Account`，实现注册、用户名预览、密码安全校验和 PostgreSQL 持久化。

旧 `/users` 内存接口默认下线，仅保留 `User`、`UserRepository`、`MemoryUserRepository` 作为测试或兼容代码，不再注册为生产 Bean。

## 主要改动

### 数据库

新增 `V2__rename_username_to_nickname.sql`：

- 将 `app_users.username` 重命名为 `nickname`
- 将空昵称回填为当前 `user_name`
- 将 `nickname` 设置为 `NOT NULL`
- 重命名对应检查约束
- 不修改已执行的 `V1`

### Account 注册链路

新增：

```text
Account
AccountRepository
JdbcAccountRepository
AccountService
AccountController
SignUpRequest
SignUpResponse
UsernamePreviewRequest
UsernamePreviewResponse
```

正式接口：

```http
POST /auth/sign-up
POST /auth/sign-up/username-preview
PATCH /accounts/{id}/nickname
```

注册请求：

```json
{
  "email": "user@example.com",
  "password": "至少 15 个字符",
  "confirmPassword": "至少 15 个字符",
  "nickname": "张三",
  "userName": "可选"
}
```

注册响应只返回：

```json
{
  "userId": 123
}
```

注册规则：

- `nickname` 必填，保存原始 Unicode 文本
- `userName` 为空时由服务端生成
- 用户手动填写的 `userName` 必须符合 `^[a-z0-9_]+$`
- 手动填写的用户名冲突时返回 `409 Conflict`，不自动改写
- 自动生成的用户名冲突时追加随机数字并重试
- `user_name` 创建后不可修改
- `nickname` 通过单独接口修改
- `confirmPassword` 不进入模型、数据库或日志

### 用户名拉丁化

使用 ICU4J：

```text
Any-Latin; Latin-ASCII
```

处理流程：

```text
NFKC
→ ICU 转写
→ 小写化
→ 非 a-z/0-9 转为 _
→ 合并连续 _
→ 删除首尾 _
→ 限制长度
→ 检查唯一性
```

预览接口为无状态接口：

```json
{
  "nickname": "张三"
}
```

返回：

```json
{
  "userName": "zhang_san",
  "available": true
}
```

前端对输入停止约 500ms 后调用预览接口，但预览不占用用户名；最终注册仍必须由数据库唯一约束保证。

### 密码策略

遵循 NIST SP 800-63B-4：

- 单因素密码最少 15 个 Unicode code point
- 允许 Unicode、空格和长密码，至少支持 64 个字符
- 不强制大小写、数字、特殊字符组合
- 使用 NFC 规范化后再哈希
- 使用 Argon2id 保存密码哈希
- 使用版本化本地 blocklist 拒绝常见、项目相关和已知弱密码
- 不调用外部密码泄露查询服务
- 不记录明文密码

NIST 当前规范明确要求单因素密码至少 15 个字符，并要求使用常见或泄露密码阻止列表。[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

### Repository

`JdbcAccountRepository` 使用 `JdbcTemplate` 和 PostgreSQL：

- `INSERT ... RETURNING user_id`
- `findById`
- `findByEmail`
- `existsByUserName`
- `updateNickname`

保留 `AccountRepository` 接口，避免 Service 直接依赖 JDBC。

不引入 ORM，不使用 Spring Security Starter，密码部分只引入 Spring Security Crypto 与 Argon2 所需 provider。

## 测试计划

新增或调整：

- 用户名拉丁化测试：中文、英文重音、俄文、混合文字、符号、空结果
- AccountService 测试：字段校验、密码确认、NFC、密码 blocklist、用户名生成
- 注册 Controller 测试：`201`、只返回 `userId`、响应不包含密码
- 用户名预览测试：自动生成、冲突、手动用户名可用性
- 数据库 Repository Testcontainers 测试：插入、查询、唯一约束、昵称更新、用户名不可更新
- Flyway 测试从检查 V1 改为检查 V1+V2 和 `nickname` 字段
- 保留旧 `User` 与 `MemoryUserRepository` 的单元测试，但不再作为 Spring 应用上下文 Bean

验收标准：

- 重复邮箱或用户名返回 `409`
- 用户名创建后没有普通更新路径
- 昵称可独立修改
- 数据库中没有明文密码
- 全部测试通过，且 Testcontainers 使用 PostgreSQL 18.6

## 已确认的改进与假设

当前前端已落地用户名预览的约 500ms 防抖、过期请求取消、Unicode 密码校验和注册结果反馈，见 [`前端界面设计.md`](前端界面设计.md)。本文“只引入 Spring Security Crypto、不使用 Security Starter”描述的是注册阶段的历史方案；当前代码已按登录业务链启用完整 Spring Security 和 Redis Session，以代码和登录文档为准。

- `/users` 旧内存接口默认下线，而不是与数据库实现并存。
- 用户名预览不做预留，最终提交可能因并发返回冲突，前端重新预览即可。
- 现有 `V1` 不修改，只通过 V2 迁移完成字段改名。
- 当前 Maven Wrapper 在本机执行失败，系统 Maven 可用；实现验证阶段先使用 `mvn test`，Wrapper 修复作为独立工具链问题处理。
